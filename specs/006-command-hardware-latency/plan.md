# Implementation Plan: Command Hardware Latency

**Branch**: `feature/006-command-hardware-latency` | **Date**: 2026-04-25 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/006-command-hardware-latency/spec.md`

## Summary

Replace the flat `CommandSpeedUpgrade` scalar with a three-axis hardware tier system (CPU 1–5, Internet 1–5, GPU 0–3). Each command has a defined base time and a set of applicable modifiers; effective latency = `Clamp(baseTime × targetResistance / playerSpeedup, 0.05, commandCap)`. Hardware shop items (11 new StoreItemSO assets) apply tier upgrades via the existing `StoreController` / `StoreService` flow. Device CPU and bandwidth tiers are generated by `LocationService` PRNG and displayed in `scan ip` output. Save schema bumped to v3 with v2→v3 migration.

## Technical Context

**Language/Version**: C# 9 (.NET Standard 2.1, Unity 6 scripting runtime)
**Primary Dependencies**: Unity 6 (6000.4.2f1), TextMeshPro, Unity Input System, Unity Test Framework (NUnit)
**Storage**: JSON flat file via `JsonUtility` to `Application.persistentDataPath/save.json`
**Testing**: Unity Test Framework (NUnit) — EditMode tests at `Assets/Tests/EditMode/`
**Target Platform**: Desktop (Windows/Mac, Unity Player)
**Performance Goals**: 45 FPS; latency calculation is O(1) arithmetic — negligible
**Constraints**: `ICommand.Execute()` is synchronous; C# 8 default interface methods supported on .NET Standard 2.1; `JsonUtility` serialises only public fields; `[System.NonSerialized]` fields not persisted
**Scale/Scope**: 11 new store assets; 6 command files modified; 1 new service; 1 new enum; ~4 model file changes

## Implementation Phases

### Phase 1 — Model Foundation (no Unity, no runtime)

All tasks in this phase are pure model changes; they compile independently and carry no inter-task dependency.

- **A-1**: Add `CpuTier`, `InternetTier`, `GpuTier` int fields to `Player`. Delete `CommandSpeedUpgrade`. Fix all compile errors (only `GameManager.GetCommandLatency()` reads `CommandSpeedUpgrade` — temporarily replace with `0f` stub until Phase 2).
- **A-2**: Add `CpuTier`, `BandwidthTier` int fields to `Device`.
- **A-3**: Add `CpuTier`, `BandwidthTier` int fields to `DeviceSaveData`. Bump `SaveData.Version` constant from 2 to 3.
- **A-4**: Create `Assets/Scripts/Models/HardwareStat.cs` with `public enum HardwareStat { CPU = 0, Internet = 1, GPU = 2 }`.
- **A-5**: Add `HasHardwareUpgrade`, `HardwareStatAffected` (`HardwareStat`), `HardwareTierGranted` (`int`) to `StoreItem`. Add matching fields to `StoreItemSO` under `[Header("Hardware Upgrade")]`. Extend `StoreItemSO.ToModel()` to map these fields.

### Phase 2 — Core Service Layer

Depends on Phase 1 (A-1 through A-4 complete):

- **B-1**: Create `Assets/Scripts/Services/CommandLatencyService.cs`.
  - Constructor: `CommandLatencyService(Player player)`.
  - Seven static readonly float[] coefficient tables (named constants — no inline literals).
  - Base-time and cap constants per command verb/variant (named constants).
  - File-size scaling constants (`CopyReferenceSizeBytes = 10_000_000`, `CopyScaleFactor = 2.0f`).
  - `public float CalculateLatency(CommandLatencyContext context)` — routes to private per-category helper.
  - Inner readonly struct `CommandLatencyContext` (CommandVerb, SecurityLevel, TargetDevice, FileSizeBytes).
  
- **B-2**: Add default method to `ICommand`: `float GetLatency(string[] args) => 0f`.

- **B-3**: `StoreService.ApplyEffect()` — add hardware tier branch: when `item.HasHardwareUpgrade`, set `_player.CpuTier / InternetTier / GpuTier = item.HardwareTierGranted` (guarded: only if `HardwareTierGranted > current`).

- **B-4**: `LocationService.GenerateLocation()` — append per-device tier generation at the end of the device inner loop (after file generation):
  ```csharp
  device.CpuTier       = rng.Next(1, 6);
  device.BandwidthTier = rng.Next(1, 6);
  ```
  
- **B-5**: `LocationService.ToSaveData()` — copy `dev.CpuTier` and `dev.BandwidthTier` into `DeviceSaveData`.

- **B-6**: `LocationService.RestoreFromSave()` — set `dev.CpuTier = ds.CpuTier` and `dev.BandwidthTier = ds.BandwidthTier` (if 0 default, treat as 1 — or let migration handle it).

- **B-7**: `GameManager.MigrateIfNeeded()` — extend for v2→v3:
  - `if (Player.CpuTier == 0) Player.CpuTier = 1;`
  - `if (Player.InternetTier == 0) Player.InternetTier = 1;`
  - For each `DeviceSaveData` in all networks: `if (ds.CpuTier == 0) ds.CpuTier = 1; if (ds.BandwidthTier == 0) ds.BandwidthTier = 1;`
  - Bump migration guard to `>= 3`.

- **B-8**: `GameManager` — add `public CommandLatencyService CommandLatencyService { get; private set; }` accessor. Construct instance in `Bootstrap()` after Player is loaded: `CommandLatencyService = new CommandLatencyService(SaveData.Player);`. Remove `GetCommandLatency()` and `BaseCommandLatencySeconds` (compile errors resolved in Phase 3/4).

### Phase 3 — Command Latency Overrides

Depends on Phase 2 (B-1, B-2 complete):

All six commands receive `CommandLatencyService latencyService` as the last constructor parameter. The `null`-guard pattern: if `latencyService == null`, `GetLatency` returns `0f` (safe fallback for tests that don't need latency).

- **C-1**: `CrackCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - Parse security level from `args[0]` (WEP/WPA/WPA2 → `SecurityLevel`).
  - Build context with `CommandVerb = "crack"`, `SecurityLevel = secLevel`, `TargetDevice = null`, `FileSizeBytes = 0`.
  - Return `_latencyService?.CalculateLatency(context) ?? 0f`.

- **C-2**: `ScanCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - Detect area vs ip/mac: `args.Length == 0` (area) or `args[0] == "ip" / "mac"`.
  - For ip/mac: look up target device by `args[1]` from `_locationService` (may be null if not yet found).
  - Build context with appropriate verb variant and target device.

- **C-3**: `InjectCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - `args[0]` is IP; look up device.
  - Build context with `CommandVerb = "inject"`, target device.

- **C-4**: `FirewallCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - Same pattern: look up device by IP from args.

- **C-5**: `LsCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - Look up device (from args or first scanned device if interactive path). If device not resolvable at pre-execution time, use `targetDevice = null` (service defaults to tier-1 neutral).

- **C-6**: `CopyCommand` — add `CommandLatencyService` param. Override `GetLatency`:
  - Look up device and file by args. Pass `FileSizeBytes = file?.SizeBytes ?? 0`.

### Phase 4 — TerminalController Integration

Depends on Phase 3 (C-1 through C-6 complete; Phase 2 B-8 complete):

- **D-1**: Update `TerminalController.OnSubmit`:
  - Replace:
    ```csharp
    float latency = GameManager.Instance != null
        ? GameManager.Instance.GetCommandLatency()
        : 0f;
    ```
  - With:
    ```csharp
    float latency = 0f;
    if (GameManager.Instance != null)
    {
        var tokens = input.Trim().Split(' ');
        var cmd = GameManager.Instance.CommandParser.GetCommand(tokens[0]);
        if (cmd != null)
        {
            var args = new string[tokens.Length - 1];
            System.Array.Copy(tokens, 1, args, 0, args.Length);
            latency = cmd.GetLatency(args);
        }
    }
    ```
  - Requires `CommandParser.GetCommand(string verb)` public accessor (see D-2).

- **D-2**: Add `public ICommand GetCommand(string verb)` to `CommandParser` returning `null` if not registered (read-only lookup of the internal dictionary).

- **D-3**: `GameManager.RegisterCommands()` — pass `CommandLatencyService` as last arg to all six latency commands. Update existing constructor calls.

### Phase 5 — Display and Shop Assets

Depends on Phase 2 (B-4, B-5, B-6 for device tiers) and Phase 3 (C-2 for scan output):

- **E-1**: `ScanCommand.Execute()` — in the `scan ip/mac` output block (where device properties are printed), add after existing output:
  ```
  CPU Tier:  {device.CpuTier}/5
  BW Tier:   {device.BandwidthTier}/5
  ```

- **E-2**: Create 11 `StoreItemSO` assets in `Assets/Resources/StoreItems/` (see data-model.md Entity 4 for IDs, names, prices). Each asset has `Category = PCComponent`, `HasHardwareUpgrade = true`, and appropriate `HardwareStatAffected` + `HardwareTierGranted`. Description must state which commands are affected (FR-014).

### Phase 6 — Tests and Quality Gates

Depends on Phase 2 (B-1) and Phase 3 (all C tasks):

- **F-1**: Create `Assets/Tests/EditMode/CommandLatencyServiceTests.cs`:
  - Base player (CPU1, Internet1, GPU0) — verify each command's base time is returned.
  - Max player (CPU5, Internet5, GPU3) — verify crack = base/20, inject = base/20.
  - Clamp floor: verify time never drops below 0.05f.
  - FR-021: tier-1 target device returns same time as null target (no overhead).
  - SC-005: tier-5 target CPU yields ≤ 2× resistance on inject.
  - 20× ratio check: `CalculateLatency(maxPlayer, crack WPA2)` × 20 ≤ `CalculateLatency(basePlayer, crack WPA2)` + epsilon.

- **F-2**: Add to `Assets/Tests/EditMode/StoreServiceTests.cs`:
  - Purchase hardware item with CPU tier 2: verifies `Player.CpuTier == 2`.
  - Purchase hardware item with lower tier than current: verifies tier unchanged.
  - Purchase same hardware item twice: verifies `PurchasedItems` guard prevents double application.

- **G-1**: Update `HelpCommand` registered entries to mention that hardware upgrades affect command speed (summary line; no full latency detail in help output).

- **G-2**: XML documentation on `CommandLatencyService` public members (constitution §I compliance).

- **G-3**: XML documentation on `CommandParser.GetCommand()` (new public method).

- **G-4**: Manual UX gate — before PR merge, verify in Unity Play Mode:
  - `crack WPA2` shows a noticeably longer progress bar than `ls`.
  - After purchasing CPU upgrade, crack bar is visibly shorter.
  - `scan ip` on a scanned device shows CPU Tier and BW Tier lines.
  - `show` and `help` remain instant (no progress bar).
  - Terminal output samples included in PR description.
